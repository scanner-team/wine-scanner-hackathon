# Масштабируемость

## Текущий потолок

Сервис обрабатывает один запрос за раз (`_inference_lock`). Параллельный
запуск двух тяжёлых вычислений (embedding + VLM) на одном GPU медленнее
последовательного, поэтому запросы сериализуются. На RTX 4090 полный
ответ — 1.5–6 с на фото, устойчивая пропускная способность ~0.4–0.7
запроса/с.

Это ограничение касается двух **разных** моделей на одной карте. Оно не
про способность одного vLLM-сервера батчить несколько **одинаковых**
запросов к одной модели — для этого у vLLM есть continuous batching,
который в текущей конфигурации не используется.

## Вертикальное масштабирование (оценка)

Оценка для пары H100, не измерение — реальные цифры требуют нагрузочного
теста (`vllm bench`, `locust`/`wrk`):

| Величина | Оценка | Основание |
|---|---|---|
| Глубина батча | ~8–16 запросов | VRAM H100 (80 ГБ) при модели 4B, `max_model_len=8192` |
| Задержка под полной нагрузкой | ~2–4 с | H100 ~3× быстрее по compute/пропускной способности памяти; батчинг не бесплатен |
| Пропускная способность | ~3–8 запросов/с | параллельность ÷ задержка (Little's Law) |

Вертикальный путь — разовая замена железа; следующий потолок снова
требует замены узла.

## Горизонтальное масштабирование

Несколько независимых узлов за балансировщиком. Требует доработки:
состояние сервиса сейчас локально на каждом инстансе —

- `predict_log.jsonl`, `marks_log.jsonl` — журналы на диске процесса;
- состояние пакетной обработки (`_batches`) — в памяти процесса.

Для нескольких узлов это нужно вынести в общее хранилище (БД или Redis
для батч-состояния, общий лог-стор), иначе статистика и прогресс пачек
расползутся по инстансам.

## Расчёт на устройстве пользователя

Альтернатива серверному пути: связка `MobileCLIP` + CoreML + Apple Neural
Engine (или аналог под Android) считает эмбеддинг прямо на устройстве.
Пропускная способность системы тогда не зависит от числа одновременных
пользователей, а капитальные затраты на GPU-инфраструктуру переносятся на
уже существующее железо пользователя — предельная стоимость
масштабирования по пользователям близка к нулю для владельца сервиса.
Обратная сторона: вероятно более низкая точность отдельного
распознавания, чем у `Qwen3-VL-Embedding-2B`, и такой путь не покрывает
шаг чтения этикетки (VLM). Не реализовано в этой версии.

## Итог

Для текущего объёма задачи достаточно одного узла (один запрос за раз),
задержка укладывается в лимит 10 с с большим запасом. Пути роста:
вертикальный (дороже железо, тот же потолок в перспективе),
горизонтальный (нужна доработка состояния под несколько узлов),
on-device (снимает вопрос нагрузки полностью, но не реализован).
